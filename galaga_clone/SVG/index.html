Galaga path-data, drawn from its bytecode

Three SVGs that turn the encoded fly-in / attack path data into pictures.

A Galaga enemy's flight isn't a stored curve — it's a tiny steering program: a list of 3-byte segments (vx · vy · rotRate · duration) and control tokens. Each frame the interpreter does angle += rotRate, then moves by A·cos(angle) / −A·sin(angle). So to see a path you must run it, not plot it. Each picture below was produced by feeding a real path through a faithful port of the arcade's motion model (tasks/bugMotion.js ← Z80 gg1-5.s) and recording every point. Their companion generators live beside them (gen_*.py).

Status: exploratory / proof-of-concept artifacts. They currently re-implement the motion model inline; the intended real version has the generator import bugMotion.js directly so the atlas can never drift from the game — and so it doubles as before/after proof for the pending octagonal-motion rewrite. Coordinates: 224 × 288 playfield, matching the arcade.

1 · A single fly-in path unfolds

path_01E8.svg  ·  generator: gen_path_svg.py
What
path_01E8 — the codebase's own token-free reference fly-in (PATH_INDEX entry 6, variant 0). Just four segments and an FF END.
Shows
How the four 3-byte segments compose nose-to-tail into one swoop — descend, gentle bend, hard hook, long tail — each coloured separately. The loop is drawn by the numbers, not by hand.
Also
The mirrored pair (dashed): member 1 runs the same bytes with rotation negated (the pair-member bit-7 flag) — Galaga's iconic symmetric "wishbone" entry, from one shared program.
Caveat
01E8 ends in a raw END (it's a test path), so its long tail flies off-screen; the trajectory is clipped at the playfield edge.

2 · One bytecode, three routes

three_routes_001D.svg  ·  generator: gen_three_routes.py
What
path_001D — a Type-2 fly-in carrying two conditional branch tokens, so the same bytes encode three mutually-exclusive flights.
Shows
A shared grey trunk, then two forks back-to-back: at F7 a transient bug peels off (swoops, targets the player, and leaves off-screen); ~2 frames later at F0 the formation bugs split by stage — 1–7 vs 8+ — both homing into the same slot.
Why
This is the galaga-only richness a static format can't express: a path is control flow. Gates: F7 = (objId&0x38)==0x38; F0 = stage ≥ 8. (It mirrors the 3-route table in research_flyin_dataflow.md.)
Caveat
The two forks sit ~4 px apart because segment C is a 2-frame burst; the transient's player-targeting used a fixed player X, and both formation routes home to one example slot.

3 · The F3 player-targeting fan

f3_fan.svg  ·  generator: gen_f3_fan.py
What
ATTACK_PATH_RED — the red-moth attack dive, driven by the F3 (BREAK_TARGETED) token. The continuous axis, vs. the discrete branches above.
Shows
The same dive run for seven player positions. F3 reads your X, buckets (playerX − mothX)/4 into 0–7, and picks a turn-hold duration from an 8-byte LUT (63 → 34 frames). A longer hold runs the rot −6 turn longer → the dive hooks harder toward your column. The dives fan out tracking the player.
Key
F3 sets the turn's duration, not its heading — so the dive biases toward you rather than homing exactly, and the aim cone saturates (the LUT clamps) at the screen edges.
Caveat
Launched from a central slot so the fan spreads symmetrically; the player marker colours match each dive.

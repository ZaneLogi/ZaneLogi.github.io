DESIGN RATIONALE  ·  why the JS port mirrors this scheduler 1:1
  • 1:1 mapping to Z80 functions — each f_xxxx in the original becomes one JS module under tasks/. Verification is mechanical: read the Z80, port the logic, cite the source line. Diverging from this mapping makes faithfulness impossible to check.
  • Tasks without Z80 counterparts (CPU1 stand-ins) — the original Galaga ran on two Z80s; CPU1 handled bullet movement (rckt_man) and collision (hitd_det_rckt) in parallel with CPU0's task scheduler. Our single-threaded JS port folds that work into new tasks (e.g. bulletUpdate) that have no f_xxxx slot in the Z80 task table. These are the only acceptable deviations from the 1:1 rule above — each one is labeled with a comment naming the CPU1 function it represents, and slotted in dispatch order to reproduce the natural CPU0/CPU1 lag.
  • Per-task enable flag — every task can be toggled live in the dev panel. Invaluable for isolating bugs: "disable formation pulse and see if collision still works", "turn everything off except player move and starfield", etc. Mirrors the Z80's ds_cpu0_task_actv bitmap.
  • Deterministic dispatch order — same sequence every tick, so ordering-dependent bugs reproduce across runs. The Z80 walks d_cpu0_task_table in fixed slot order; our TASK_TABLE follows the same order.
  • Self-throttling via frame counter — tasks gate themselves with frameCount % N to run at sub-rates (15 Hz formation drift, 2 Hz game timers). One scheduler at 60 Hz, no separate timer infrastructure — exactly how the Z80 handles it.
  • Slot ordering matters in single-threaded JS — the original ran CPU0 and CPU1 in parallel; we're sequential. Position in the table becomes load-bearing. Example: bulletUpdate (CPU1 stand-in) sits right after playerFire so a freshly spawned bullet doesn't move on the same tick — preserving the natural CPU0/CPU1 1-frame lag instead of accidentally collapsing it.
  • Shared mutable state — all tasks read/write a single global state object. No encapsulation, no message passing — exactly like Z80 RAM. The dev panel + the discipline of citing Z80 sources are what keep this from devolving into spaghetti.

WHERE THE CODE LIVES  ·  quick map from this section's research findings to the JS implementation
 • paths.js — all 22 ported db_flv_XXXX data blocks, the 24-entry PATH_INDEX (db_2A3C), the 8-entry VARIANTS table (db_2A6C), the 96-byte SPRT_FMTN_HPOS + getObjectIdForSlot(), and getPathByIndex().
 • tasks/bugMotion.js — per-tick interpreter (CPU1 f_08D3 stand-in): segment loop, token dispatch (0xFF END / 0xFB TURN_HOME / 0xFD/0xF7/0xF0 2-byte arg skip), X/Y alternation. Exports launchEnemy(state, objectId, pathIndex) — the public API for "put this enemy into flight".
 • tasks/launchAttackWave.js — wave runner (f_2916 stand-in). Currently walks a hardcoded TEST_WAVE; the integration pass (after step 8) replaces this with a stage-data-driven state.waveTable.
 • tasks/objectStates.js — render dispatch by enemy state ('formation' uses homeX/Y + offsets, 'flying' uses live x/y, 'dead' is skipped).
 • state.js — per-enemy schema includes objectId, state, motion fields (x,y,vx,vy,angle,rotRate,pathBase,pathOffset,segTimer), and the bugMotion task flag.
 • main.js — TASK_TABLE slot order: objectStates → bugMotion → enemyStatus → … → playerFire → bulletUpdate → launchAttackWave. launchAttackWave sits after bugMotion for natural 1-tick lag on newly-spawned enemies.
PATH TABLE HIERARCHY  ·  fly-in vs. attack are separate tables
Fly-in: db_2A3C is a 24-entry pointer index, not raw path data. Each entry packs a 13-bit address pointing into the db_flv_XXXX path-data blocks plus a 3-bit variant flag (bits 13–15) that selects a transform from db_2A6C — variants flip / mirror a single block so one definition can serve symmetric entrance patterns. Pattern blocks are ~25–54 bytes each and terminate with 0xFF 0xFF.
Source: gg1-3.s:1918–1928 (index + variant table) · gg1-5.s:82–2893 (data blocks).
Attack dives: db_flv_atk_yllw and db_flv_atk_red — completely separate tables for yellow / red alien dive sequences, with attack-specific opcodes (0xF2–0xF4) layered on top of the shared 3-byte segment format.
Source: gg1-5.s:285, 311 · referenced from gg1-2_fx.s:976, 1007.

PATH INTERPRETER  ·  per-tick advance
Driver task f_08D3 (gg1-5.s:1422) iterates ds_bug_motion_que each tick. For each active enemy, dispatch enters at mctl_fltpn_dspchr (gg1-5.s:1459) and runs:
  1. Decrement segment timer (dec 0x0D(ix)). If non-zero, skip to step 3.
  2. Load next 3-byte segment from path pointer 0x08-09 (gg1-5.s:1996–2025). Byte0 lo-nibble → X vel (0x0A), hi-nibble → Y vel (0x0B); byte1 → rotation rate (0x0C); byte2 → new timer (0x0D). Pointer always advances 3 bytes; tokens (≥ 0xEF) are dispatched via d_0920_jp_tbl instead of being treated as segment data.
  3. Add rotation rate to angle (0x0C → 0x04-05; gg1-5.s:2080–2102). Angle is a 10-bit value (1024/circle).
  4. Pick sprite frame from angle: 10-bit angle → 8 wing-pose frames via quadrant bits + divide-by-~42 (gg1-5.s:2104–2148). Flip flags in 0x13 mirror frames horizontally / vertically.
  5. Apply velocity to position (gg1-5.s:2150–2234). Velocity nibbles are signed 4-bit (−8..+7); sign-extended via sra + adc when added to the 9.7 fixed-point position word. Note: X and Y are applied on alternate frames (not both each tick), driven by frame-counter parity — same trick as the player dxFlag 1/2 px alternation.
Key finding: X/Y velocity is independent of the heading — rotation only affects which sprite is drawn, not the direction of motion. Enemies can drift sideways while visually pointing forward. Our JS port doesn't need a sin/cos lookup; just apply the segment's velocity bytes directly.

WAVE LAUNCHER  ·  f_2916 (gg1-3.s:1658)  ·  per-tick task slot 0x08
Reads pairs sequentially from ds_8920 and spawns enemies into the active flight queue. Pure state machine — no scripted timing; advances when the queue drains.
Pair launch — two enemies, mirrored paths
Each "pair" in ds_8920 is actually two 4-byte tokens: [B1, U1, B2, U2]. Both enemies launch simultaneously; the second uses a flipped variant from db_2A6C — same path data, different mirror / rotation flags. This is what produces Galaga's iconic two-by-two arc entrance.
Source: gg1-3.s:1749, 1881; variants gg1-3.s:1928.
Launch timing — pull-based, not scripted
Normal stages: next pair launches when b_bugs_flying_nbr == 0 (wait for current pair to reach HOME) + 2-frame gap via ds4_game_tmrs[0].
Wave transition: 0xFF end-token → wait for all flying bugs to land → advance cursor to next wave (0x7E start-token).
Stage end: 0x7F final-wave token → f_2916 disables itself in the task table.
Source: gg1-3.s:1662–1695, l_2A29.
Active flight queue
ds_bug_motion_que: 12 slots × 0x14 bytes. f_2916 scans for first inactive (bit 0 of 0x13 == 0); if full, aborts launch this tick.
Heads-up: only 12 enemies in flight at once — not all 48. Pair launching works because pairs share two slots; the queue is bounded.
Source: gg1-3.s:1736–1745.
Formation slot assignment
Pre-stored at launch (not computed later). Object ID (struct byte 0x10) indexes into sprt_fmtn_hpos lookup; home Y / X copied to enemy struct at launch time. So when the path interpreter hits HOME (0xF1) or END (0xFF), the destination is already known.
Source: gg1-3.s:1552–1556, 1761; lookup gg1-5.s:185.
Key port implication: wave progression is pull-based, gated on the in-flight count rather than a frame counter. Our JS port should mirror this: increment flyingCount when launching, decrement when reaching HOME, only advance the cursor when count == 0 (+ small frame gap). This naturally produces the right pacing without per-stage timing data.
OBJECT ID ↔ FORMATION SLOT  ·  sprt_fmtn_hpos lookup (gg1-5.s:185)
The 96-byte table at sprt_fmtn_hpos is the single source of truth for "which formation slot does this object go to?". Used by the wave launcher to set homeX / homeY at launch, and by the path interpreter when HOME tokens fire.
Indexing scheme
Object IDs are byte offsets into the table (not entry indices). All IDs are even — entry N occupies bytes 2N, 2N+1.
 • ID range: 0x08 – 0x5E (48 IDs, all even)
 • Table size: 96 bytes = 48 entries × 2
 • Each entry: (Y_code, X_code)
 • Lookup: a = sprt_fmtn_hpos[ID] reads Y; next byte reads X.
 • Source: gg1-5.s:1553 — ld e,0x10(ix); ld a,(de)
Y / X codes (NOT pixels)
Y_code = 0x14 + 2*rowIdx  → 0x14, 0x16, 0x18, 0x1A, 0x1C, 0x1E for rows 0–5 (boss / boss / butterfly / butterfly / wasp / wasp).
X_code = 2*colIdx  → 0x00, 0x02, … , 0x12 for cols 0–9.
Canvas pixel position is derived later via state.js's existing transforms (Y formula + −16 px X offset — see research_coordinate_system.md for the verified sprite-chip formulas).
JS port plan: add an objectId field on each enemy in state.js. Either (a) inline the full 96-byte sprt_fmtn_hpos as a JS Uint8Array and use ID-as-byte-offset, or (b) compute id from (rowIdx, colIdx) via a small reverse lookup since entries are scattered (NOT just row*10+col) to optimise fly-in pairing. Recommend (a) — tiny constant, exact Z80 fidelity, no risk of mis-deriving the scatter order. Verified examples: boss row 0 entries 0–3 = (0x14, 0x06) (0x14, 0x0C) (0x14, 0x08) (0x14, 0x0A) → row 0 cols 3, 6, 4, 5 (paired ordering).

Why we can't just mirror Z80's blocking-loop pattern:

Z80's while (state == X) { } foreground works because the architecture has two concurrent execution streams we don't have:
 • Hardware-driven preemption. The video chip fires a VBL interrupt ~60 Hz regardless of what the main thread is doing. The interrupt handler runs the task scheduler (task_man.s) — so tasks like f_0977 (coin/start input) keep running even while g_main spins. Tasks update b8_9201_game_state in shared RAM; the spin loop eventually sees the change and exits. Wasteful (busy-wait) but functional.
 • Two physical CPUs. Galaga has CPU0 and CPU1 on separate chips, running their own programs out of their own ROM, communicating via shared RAM. CPU1 owns path interpretation (f_08D3) and bullet collision (hitd_det_rckt). That's why earlier steps had bugMotion and bulletUpdate tagged as "CPU1 stand-ins".

JavaScript has neither — single-threaded event loop, no preemption, all our work happens inside one requestAnimationFrame callback per frame. A while (state == X) { } would freeze the browser; rAF would never fire again. So instead we turn the state machine itself into a task that runs every tick.
Port implications (architectural):
 • Add state.gameState as enum: 'attract' | 'ready' | 'playing' | 'gameOver'. Already exists as a string field — just needs to actually drive behaviour.
 • Add state.score, state.lives, state.stage, state.bugsActive — direct mirrors.
 • Replace blocking loops with per-tick state dispatch: a new tasks/gameController.js runs every tick, switches on state.gameState, and toggles other task flags accordingly. (Z80 g_main's "block until state changes" becomes our "check state every tick".)
 • Per-state task enables become declarative: each state has a "this set of tasks should be on" config; gameController applies the diff on transition.
 • Stage-clear detection: every tick during 'playing', count enemies with state ∈ {formation, flying}; if zero and no waves pending, advance stage.
 • glbl_enemy_enbl equivalent: a state.enemyEnable flag that gates launchAttackWave running in attack mode (vs fly-in mode).

Implementation contract: when tasks/gameController.js is written, its top-of-file comment must cite this section (architecture.html §5c, "Why we can't just mirror Z80's blocking-loop pattern") so future readers understand why the state machine is a task instead of a control-flow loop. Same convention as bugMotion / bulletUpdate citing their CPU1 stand-in role.

STAGE-CLEAR DETECTION  ·  gctl_supv_stage (game_ctrl.s:1306)  ·  binary gate, called every frame
The gate is two ANDed bytes — no player-state guards (stage clears even if player is mid-capture / mid-death). Driven from gctl_game_runner per frame during IN_GAME.
gctl_supv_stage:
  ld a, (ds_cpu0_task_actv + 0x08)  ; f_2916 — attack wave launcher
  ld b, a
  ld a, (b_bugs_actv_nbr)
  or b
  jr nz, l_081B  ; jump if EITHER nonzero
  jp gctl_stg_restart_hdlr  ; both zero → stage clear
What `b_bugs_actv_nbr` counts
Counts all enemies with status NOT 0x80 (inactive). Includes:
 • 01 Formation (home)
 • 02 Rotating into position
 • 03 Spawning progression
 • 04 Dying / exploding (countdown 0x40 → 0x00)
 • 09 Diving (attack)
Snapshotted every 2 frames (gg1-3.s:1142) — not real-time. So a kill takes up to 2 frames to register, then explosion animates ~64 frames before status flips to 0x80, THEN counter ticks down.
f_2916 enable lifecycle
Self-disables at gg1-3.s:1905 when the 0x7F final-wave token is reached AND all flying bugs are home (verified step 8 item [5]).
Re-enabled ONLY at next stage init via c_2C00 (task_man.s:298). No intermediate re-enable. So the gate's task_actv[0x08] == 0 check is naturally satisfied between "wave done" and "next stage starts".
Post-clear transition flow
1. Gate fires → gctl_stg_restart_hdlr (game_ctrl.s:573)
2. Wait game_tmr_3 > 0 — 4-frame delay (game_ctrl.s:548) for last explosion residue
3. gctl_supv_score — award points (game_ctrl.s:552)
4a. Combat stage: straight to stg_init_splash → "STAGE N+1" (no "CLEARED" intermediate text)
4b. Challenge stage: branch to gctl_chllng_stg_end (game_ctrl.s:900-924) → "NUMBER OF HITS" + count + "BONUS" + points + "PERFECT!" if 40/40 → then stg_init_splash
State NOT cleaned up at stage-clear
Active bombs and rockets are left to despawn naturally — no explicit clear at stage transition. Their object status flips to 0x80 when they expire / miss. Sprite RAM clear only happens on player death / game-over paths (game_ctrl.s:621-622), not stage-clear.
Port implications:
 • Add state.bugsActive recomputed each tick: count of enemies with state ∈ {formation, flying}. (Our 'dead' state corresponds to Z80 0x80 inactive; we don't yet have an 'exploding' state — kills go straight to 'dead'.)

 • Don't carry over bombs/rockets at transition — let them despawn. No explicit clear needed (matches Z80).
 • Defer challenge stages entirely — combat-only flow first.
 • Defer the explosion state — current 'alive=false' → 'dead' transition is fine. Polish item: add an 'exploding' substate with a few-frame countdown so the visual timing matches Z80.
PLAYER DEATH / LIVES / RESPAWN  ·  hitd_fghtr_hit (gg1-5.s:730) → gctl_plyr_terminate (game_ctrl.s:587)

Death detection (gg1-5.s:730-769)

 • ship sprite code 0x20 (explosion tile)
 • sprite state b_8800 = 0x08 ("exploding")
 • explosion counter mctrl_q = 0x0F
 • "bang" SFX flag

Does NOT immediately jump — flag is polled.
Death animation (game_ctrl.s:513-514)

Lives counter (game_ctrl.s:588-592)

Respawn (game_ctrl.s:821-886)

4. plyr_respawn_rdy (game_ctrl.s:872) re-enables fire button (f_1F04), collision (f_05EE), attack waves (_b_atk_wv_enbl = 1).

ATTRACT / DEMO MODE  ·  f_17B2 (gg1-2_fx.s:188)  ·  15-state cycle with scripted demo playback
Attract mode is much richer than a static splash — it's a 15-sub-state machine that cycles logo / score-table / scripted demo gameplay / high-score display, then loops. Demo gameplay is not AI-driven; it's pre-recorded byte vectors that drive a f_1700 "scripted fighter control" task (replaces normal player input). Real fly-in / attack / bomber tasks run as in normal play, gated by glbl_enemy_enbl.
15-state cycle (selected)
demo_idx (@ ds_9200_glbls + 0x03) selects via RST 0x08 jump table d_17C3_jptbl:
 • 0x00 / 0x06 / 0x0D — clear playfield
 • 0x01 / 0x02 — sprite-table setup, cycle 5 text screens (~1 sec each)
 • 0x03 / 0x04 — 7-enemy training fly-in + wait
 • 0x05 — boss-capture sync
 • 0x07 — "GAME OVER" splash
 • 0x08–0x0B — demo gameplay setup + wait, post-capture continuation
 • 0x0C — disable enemy tasks, reset glbl_enemy_enbl=0
 • 0x0E — "GALACTIC HEROES" high-score display (~5 sec) → wraps to 0x00
Scripted demo input
Three pre-recorded input vectors (gg1-2_fx.s:265, 310, 404):
 • d_181F — post-capture demo
 • d_1887 — pre-capture demo
 • d_1928 — training (7 enemies)

Each byte: 5-bit command + 3-bit param. Commands include move L/R, fire, target-fire (fire when aimed at enemy index N), end-of-sequence (0xC0). Parsed by f_1700 task (gg1-2_fx.s:21-169).
Coin handling (already partly known from item [1])
f_0977 polls ds3_99B5_io_input + 0x00 every tick. On coin detected during ATTRACT, sets game_state = 2 (READY). Does NOT interrupt mid-cycle — the attract state machine keeps running until the blocking loop in g_main sees the new state byte.
